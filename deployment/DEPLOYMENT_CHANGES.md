# Cambios al repositorio para despliegue en AWS EC2

Este documento describe todos los cambios realizados sobre el fork de [DefectDojo](https://github.com/DefectDojo/django-DefectDojo) para permitir su despliegue en una instancia EC2 con RDS PostgreSQL usando CloudFormation y Docker Compose.

## Cambio 1 — Versión de Python base (todos los Dockerfiles)

**Problema:** Los Dockerfiles usaban la imagen `python:3.15.0b1` (beta), para la cual la mayoría de wheels binarios de las dependencias Python no estaban disponibles en PyPI. Esto provocaba fallos de compilación con Rust/GCC durante el `pip install`.

**Archivos modificados:**
- `Dockerfile.django-debian`
- `Dockerfile.nginx-debian`
- `Dockerfile.django-alpine`
- `Dockerfile.nginx-alpine`
- `Dockerfile.integration-tests-debian`

**Cambio:**
```diff
- FROM python:3.15.0b1-slim-bookworm@sha256:... AS base
+ FROM python:3.12-slim-bookworm AS base

- FROM python:3.15.0b1-alpine3.22@sha256:... AS base
+ FROM python:3.12-alpine3.22 AS base
```

## Cambio 2 — Dependencias de desarrollo XML (Debian y Alpine)

**Problema:** La librería Python `lxml` (y otras dependencias XML) requieren las cabeceras de desarrollo de `libxml2` y `libxslt` para compilar desde fuente. Su ausencia causaba errores como:
```
fatal error: libxml/xmlversion.h: No such file or directory
```

**Archivos modificados:**
- `Dockerfile.django-debian`
- `Dockerfile.nginx-debian`

```diff
+    libxml2-dev \
+    libxslt1-dev \
```

- `Dockerfile.django-alpine`
- `Dockerfile.nginx-alpine`

```diff
+    libxml2-dev \
+    libxslt-dev \
```

## Cambio 3 — Variables HOME y XDG_CACHE_HOME en Docker Compose

**Problema:** El SDK de Azure DevOps (usado por DefectDojo para integraciones) intenta escribir caché en el directorio HOME del usuario del contenedor. En los contenedores Django, el usuario no tiene un HOME válido (`/nonexistent`), lo que causaba errores de permiso durante la inicialización:
```
PermissionError: [Errno 13] Permission denied: '/nonexistent'
```

**Archivo modificado:** `docker-compose.yml`

**Cambio:** Se agregaron las variables de entorno `HOME` y `XDG_CACHE_HOME` en los 4 servicios Django del compose:

```diff
 services:
   uwsgi:
     environment:
+      HOME: /tmp
+      XDG_CACHE_HOME: /tmp/.cache

   celerybeat:
     environment:
+      HOME: /tmp
+      XDG_CACHE_HOME: /tmp/.cache

   celeryworker:
     environment:
+      HOME: /tmp
+      XDG_CACHE_HOME: /tmp/.cache

   initializer:
     environment:
+      HOME: /tmp
+      XDG_CACHE_HOME: /tmp/.cache
```

## Cambio 4 — Migración de base de datos faltante (0277)

**Problema:** El contenedor `initializer` ejecuta `manage.py makemigrations --check` para validar que no haya modelos con cambios sin migración. En este fork existía una divergencia en los modelos (`answer`, `choiceanswer`, `choicequestion`, `textanswer`, `textquestion`) respecto a la última migración del repositorio upstream. Esto detenía la inicialización con error:
```
You made changes to the models without creating a DB migration for them.
```

**Archivo creado:** `dojo/db_migrations/0277_alter_answer_options_alter_choiceanswer_options_and_more.py`

**Contenido (generado con `manage.py makemigrations`):**
```python
# Generated by Django 5.1.15 on 2026-05-29 20:42
from django.db import migrations

class Migration(migrations.Migration):
    dependencies = [
        ("dojo", "0276_riskacceptanceengagement_path_and_more"),
    ]
    operations = [
        migrations.AlterModelOptions(name="answer", options={}),
        migrations.AlterModelOptions(name="choiceanswer", options={}),
        migrations.AlterModelOptions(name="choicequestion", options={}),
        migrations.AlterModelOptions(name="textanswer", options={}),
        migrations.AlterModelOptions(name="textquestion", options={}),
    ]
```

## Cambio 5 — Valores por defecto en entrypoints de uwsgi

**Problema:** El script `docker/entrypoint-uwsgi.sh` construye el comando `uwsgi` usando las variables `DD_UWSGI_MODE`, `DD_UWSGI_ENDPOINT` y `DD_UWSGI_HTTP`. Si alguna de estas no está definida en el entorno del contenedor (por ejemplo, en el sabor Debian donde el `Dockerfile.django-debian` no las exportaba todas), `uwsgi` arrancaba con argumentos vacíos o inválidos y moría con:
```
unable to load configuration from
```

**Archivos modificados:**
- `docker/entrypoint-uwsgi.sh`
- `docker/entrypoint-uwsgi-dev.sh`

**Cambio:**
```diff
 python3 manage.py check

+DD_UWSGI_MODE="${DD_UWSGI_MODE:-socket}"
+DD_UWSGI_ENDPOINT="${DD_UWSGI_ENDPOINT:-0.0.0.0:3031}"
+DD_UWSGI_HTTP="${DD_UWSGI_HTTP:-0.0.0.0:8081}"
```

## Archivo nuevo — Plantilla de infraestructura CloudFormation

**Archivo creado:** `dd_deploy_ec2.yaml`

Este archivo **no existía en el repositorio original** y fue creado desde cero para automatizar el despliegue en AWS. Provisiona:

| Recurso | Tipo AWS |
|---------|----------|
| VPC + subnets públicas (2 AZs) | `AWS::EC2::VPC`, `AWS::EC2::Subnet` |
| Internet Gateway + rutas | `AWS::EC2::InternetGateway`, `AWS::EC2::Route` |
| Security Groups (EC2, RDS, ALB) | `AWS::EC2::SecurityGroup` |
| Instancia EC2 (`t3.large`, 120 GB gp3) | `AWS::EC2::Instance` |
| RDS PostgreSQL (`db.t3.micro`) | `AWS::RDS::DBInstance` |
| Application Load Balancer | `AWS::ElasticLoadBalancingV2::LoadBalancer` |
| Target Group (health: `/nginx_health`) | `AWS::ElasticLoadBalancingV2::TargetGroup` |
| IAM Role + Instance Profile (SSM) | `AWS::IAM::Role`, `AWS::IAM::InstanceProfile` |

**Bootstrap (UserData):** La instancia EC2, al arrancar, ejecuta automáticamente:
1. Espera liberación de locks `apt`
2. Instala Docker y dependencias del sistema
3. Clona el fork del repositorio en `/opt/django-DefectDojo`
4. Escribe variables de entorno de configuración desde los parámetros del stack
5. Genera `docker-compose.override.yml` con las variables HOME/XDG_CACHE_HOME
6. Construye las imágenes localmente (`docker compose build`)
7. Levanta todos los servicios (`docker compose up -d`)

**Parámetros clave del stack:**

| Parámetro | Descripción |
|-----------|-------------|
| `DDDatabaseAdmin` | Usuario administrador de PostgreSQL |
| `DDDatabasePassword` | Contraseña de PostgreSQL |
| `DDCredentialAES256Key` | Clave AES-256 para credenciales |
| `DDSecretKey` | Django SECRET_KEY |
| `DDAdminUser` | Usuario administrador de DefectDojo |
| `DDAdminPassword` | Contraseña del administrador |
| `SSHLocation` | CIDR con acceso SSH a la instancia |
| `EC2SubnetSelector` | `1` o `2` — alterna la subnet para forzar recreación de EC2 sin eliminar el stack |
| `EC2RootVolumeSize` | Tamaño del disco raíz en GB (mínimo 30, usado 120 para builds Docker) |

## Comandos de despliegue

### Crear / actualizar el stack

```bash
aws cloudformation deploy \
  --stack-name defectdojo-test \
  --template-file dd_deploy_ec2.yaml \
  --parameter-overrides \
    DDDatabaseAdmin=ddadmin \
    DDDatabasePassword='TuPassword123' \
    DDCredentialAES256Key='unaClaveAleatoria32caracteressss' \
    DDSecretKey='otraClaveAleatoria32caracteresss' \
    DDAdminUser=admin \
    DDAdminPassword='AdminPass123' \
    SSHLocation='<TU_IP>/32' \
    EC2SubnetSelector='1' \
    EC2RootVolumeSize='120' \
    GitBranch='trunk' \
  --capabilities CAPABILITY_NAMED_IAM
```

> Para forzar la **recreación de la instancia EC2** sin eliminar el stack (útil al cambiar código), cambia `EC2SubnetSelector` entre `1` y `2` en el siguiente deploy.

### Despliegue multi-stack (una instancia por persona / rama)

Cada miembro del equipo despliega su propio stack con un nombre distinto y su rama:

```bash
# Ejemplo: instancia de Juan en su rama feature/nueva-funcionalidad
aws cloudformation deploy \
  --stack-name defectdojo-juan \
  --template-file dd_deploy_ec2.yaml \
  --parameter-overrides \
    DDDatabaseAdmin=ddadmin \
    DDDatabasePassword='PasswordJuan123' \
    DDCredentialAES256Key='claveAES256paraJuan000000000000000' \
    DDSecretKey='secretKeyParaJuan000000000000000' \
    DDAdminUser=admin \
    DDAdminPassword='AdminJuan123' \
    SSHLocation='<IP_JUAN>/32' \
    EC2SubnetSelector='1' \
    EC2RootVolumeSize='120' \
    GitBranch='feature/nueva-funcionalidad' \
  --capabilities CAPABILITY_NAMED_IAM
```

**Cada stack es completamente aislado:** tiene su propia VPC, EC2, RDS, ALB y credenciales.

**Consideraciones de costo por stack activo** (región us-east-1 aprox.):

| Recurso | Tipo | Costo/mes |
|---------|------|-----------|
| EC2 | t3.large | ~$60 |
| RDS | db.t3.micro | ~$15 |
| ALB | — | ~$18 |
| EBS 120 GB gp3 | — | ~$10 |
| **Total** | | **~$103/stack** |

> Recomendación: apagar (stop) la instancia EC2 cuando no se use y destruir el stack al terminar las pruebas para evitar costos innecesarios. RDS sigue cobrando aunque EC2 esté detenida.

### Eliminar el stack

```bash
aws cloudformation delete-stack --stack-name defectdojo-test
```

### Ver logs de bootstrap de la instancia (desde la EC2 vía SSH)

```bash
tail -f /var/log/cloud-init-output.log
```

## Operaciones post-despliegue

### Resetear contraseña del admin (si ya existía en DB)

Cuando el `initializer` detecta que el usuario admin ya existe, no actualiza su contraseña. Para resetearla:

```bash
cd /opt/django-DefectDojo
sudo docker compose exec -T uwsgi python manage.py shell <<'PY'
from django.contrib.auth import authenticate, get_user_model
U = get_user_model()
u = U.objects.get(username="admin")
u.is_staff = True
u.is_superuser = True
u.is_active = True
u.set_password("NuevaPassword123")
u.save()
print("password actualizado")
print("auth ok:", bool(authenticate(username="admin", password="NuevaPassword123")))
PY
```

> Nota: Evitar caracteres `!` directamente en la línea de comandos de bash por conflicto con history expansion. Usar heredoc (`<<'PY'`) como en el ejemplo, o ejecutar `set +H` antes del comando.

### Reconstruir imágenes tras cambios de código

No siempre es necesario reconstruir todo. Depende de qué cambió:

| Tipo de cambio | Comando |
|----------------|---------|
| Código Python/Django (vistas, modelos, parsers, templates) | `docker compose build uwsgi && docker compose up -d --no-deps uwsgi celeryworker celerybeat` |
| Configuración o assets de Nginx | `docker compose build nginx && docker compose up -d --no-deps nginx` |
| Cambios en `requirements.txt` (nuevas dependencias) | `docker compose build --no-cache && docker compose up -d` |

**Arquitectura de imágenes:**
- `Dockerfile.django-debian` es la imagen base compartida por `uwsgi`, `celeryworker`, `celerybeat` e `initializer`.
- `Dockerfile.nginx-debian` es independiente y solo lo usa el servicio `nginx`.
- Al reconstruir solo `uwsgi`, Docker reutiliza las capas de pip y sistema operativo — el rebuild es rápido porque solo recopia el código.

### Verificar estado de los servicios

```bash
cd /opt/django-DefectDojo
sudo docker compose ps -a
sudo docker compose logs --tail=100 uwsgi
sudo docker compose logs --tail=100 initializer
```

## Notas de seguridad

- El volumen raíz EC2 está configurado con `Encrypted: true` (`gp3`).
- El Security Group de RDS sólo acepta conexiones desde el Security Group de EC2 (nunca expuesto a internet).
- `SSHLocation` debe restringirse al IP del administrador; el valor `0.0.0.0/0` en el parámetro Default está sobrescrito en el comando de despliegue.
